### The grant landed, and the capability gate proved its worth

Session one shipped with the Graph credential READ-ONLY and event creation as a
capability-gated stub. Michael granted `Calendars.ReadWrite` between sessions. The
roles claim now reads `["Calendars.Read", "Calendars.ReadWrite"]`, and **not one
line of `lib/booking/outlook.ts` changed to make writing start working** — the
gate reads the tenant's own claim, so the code began writing on its next token.
That was the whole argument for gating on the claim instead of hardcoding a stub,
and it held.

The gate stays. It is not scaffolding: if the grant is ever revoked, createEvent
goes back to refusing before it fires, the reason reaches `calendar_detail`, and
the reconcile job stops hammering a wall.

Write capability was confirmed independently before anything was built on it
(create 201, read back, delete 204, verify 404) because a tenant-level grant can
still be blocked by an ApplicationAccessPolicy. It is not.

### What shipped

**Confirmation mail with an ics.** `lib/booking/email-copy.ts` is pure and
copy-gated; `lib/booking/email.ts` sends through Resend from Michael with
reply-to Michael, so a reply reaches a person. `lib/booking/ics.ts` builds the
VEVENT by hand (no calendar library in this repo): `METHOD:REQUEST` with a stable
UID so a reschedule UPDATES the client's calendar entry rather than adding a
second one beside it, `SEQUENCE` rising on every change so a client actually
accepts the update, `METHOD:CANCEL` on a cancellation so the entry is removed
rather than left as a ghost. No conferencing anywhere, asserted by test. Line
folding measures OCTETS and never splits a code point, which is the bug that
works in testing and breaks on the first name with an accent.

**Reschedule and cancel**, off the session-one token: shape-gated, sha256
compared, raw token never sent to the database. Reschedule is an IN-PLACE move,
deliberately — cancel-then-create would mint a new token and break the link
already sitting in the client's inbox. The move re-runs every rule a fresh
booking runs and lands under the same partial unique index.

**Server-side prefill**, replacing session one's id-only limitation. The link
still carries only opaque record ids; the name, email, and number are fetched
server-side from Zoho and rendered into the form. Personal data never touches the
URL or the token payload.

**Zoho linkage.** Tokened bookings write a Note on the Contact and, where there
is one, the Deal. Untokened bookings create a Lead. `createZohoNote` is new —
nothing in the repo created a Note before, that lived in n8n. Consent writes the
four `CASL_*` fields with method `Express`, source, and the exact sentence the
person read. **No Zoho Tasks are created anywhere in this flow.**

**The reminder and reconcile jobs**, plus the hourly n8n workflow that calls them.

### Decisions worth naming

**The cron route reuses `UW_BRIDGE_SECRET`.** This session cannot provision
environment variables, and the alternative — putting `FOXCA_OPERATOR_SECRET` into
an n8n credential — would copy the database's master key into a second system to
solve a scheduling problem. The cost, stated rather than buried: a leak of that
secret now also unlocks these two jobs. The blast radius is bounded — the route
cannot create, move, or cancel a booking, and returns counts and ids, never a
client's details. **Session three should give booking its own secret.**

**Consent is only ever written on a tick.** There is deliberately no false branch
anywhere in `lib/booking/zoho-link.ts`. An unticked box writes nothing: it does
not clear a date, does not set a method to none, does not touch `Email_Opt_Out`.
Absence of consent is not withdrawal of consent.

**The mail and Zoho steps are awaited, not fired and forgotten.** A serverless
function that has already returned may be frozen before background work runs, and
a lost confirmation is worse than a slower confirm.

**A booking is not an obstacle to its own move** — and it exists in two places, a
row and a calendar event. Session two initially excluded only the row, which
silently withheld the slots either side of the client's current time from the one
person entitled to take them. Caught in the live test (23 slots offered instead of
25), fixed by carrying the provider event id through `BusyInterval` and excluding
both. The manage endpoint and the reschedule engine share the same two helpers, so
the page cannot offer a time the server would refuse.

### The live write test

Run end to end against the real calendar, the real Zoho org, and real Resend.

- **Tokened booking**, through the real page with a real prefill link: form
  arrived filled from Zoho, URL carried only ids, calendar event created at the
  right instant with the phone number in the body and the location, Note written
  on the Contact with the `Booking: ` title prefix, and CASL stamped
  `Express` / dated / sourced / with the verbatim consent sentence. **This also
  settled the open question from discovery about whether the Notes `Parent_Id`
  metadata quirk blocks a write. It does not, via the related-list endpoint.**
- **Untokened booking**, to a real inbox: `lead created`,
  `confirmation_sent = true`, calendar written.
- **Reschedule**, through the manage page: row moved, `original_starts_at` kept,
  `rescheduled_count` 1, old calendar event removed and a new one written, mail
  sent.
- **Cancel**: status cancelled with reason and `cancelled_by`, calendar event
  deleted and the id cleared, `calendar_detail` "cancelled, event removed".
- **Reminder guard**, the behaviour the brief calls out: two bookings identical
  except for when they were created. The one created three days ahead was
  reminded and stamped; the one created inside the 24 hour window was
  `considered: 0`. A second run of the job reminded nobody, which is the
  idempotency guard.
- **Reconcile**: a row forced to `pending_retry` was drained on the next run,
  `considered 1, succeeded 1`.
- **Cron auth**: wrong secret 401, missing secret 401, correct secret 200 with the
  structured log.
- **Resend rejects `example.com`** by policy. The first booking's client mail
  therefore failed — and did so honestly: logged, booking unaffected,
  `confirmation_sent_at` correctly not stamped. That was an unplanned but useful
  proof that the mail step cannot fail a booking.

**Cleaned up, verified gone:** 2 calendar events (0 remaining), 1 Zoho contact
(204), 1 Zoho lead (204), 4 booking rows (table empty). The Zoho contact carried
the test Note and the test CASL consent, so both went with it.

### Known residual, for session three

If a calendar create SUCCEEDS at Graph but the response is lost in transit, the
row records `pending_retry` while an event exists, and the next reconcile run
creates a duplicate. Rare, and not reachable through any tested path, but real.
The fix is an idempotency key on the create, or a search-before-create in the
reconcile job.
