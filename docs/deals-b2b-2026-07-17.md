# B2b — The Deals surface, Direction 2 ("the control room") (2026-07-17)

Michael chose Direction 2 with one amendment: the fonts are the website's own pair
(Poppins headings, Montserrat body), not IBM Plex. This session makes that direction the
real Deals surface and deal room. Presentation plus ONE read-only field addition
(`Compliance_Status`) and the next-action deep links. No gate, fetcher-query, or authz
changes beyond that; no Zoho or workbench writes; no route path changes; no new env vars.

## Findings first

1. **`Compliance_Status` exists live** on Potentials as a picklist with a RICHER
   vocabulary than the brief's four states: `Pending Review`, `In Review`, `Approved`,
   `Rejected`, `Re-Review Needed` (plus `-None-`). Verified from the live field metadata
   before building. All six values map (`complianceStateFor` in
   [lib/deals-surface.ts](../lib/deals-surface.ts)): unset → not started; the two review
   values → under review (raw value shown verbatim); `Rejected` and `Re-Review Needed` →
   the rejected loop (amber, the step loops back); an unknown future value reads as
   in-motion and renders verbatim; an unreadable field or missing Zoho link is its own
   honest "not read" state, never a guess. A sibling `Compliance_Package_Status` field
   also exists — the brief names `Compliance_Status`, so that is what the card reads.
2. **Montserrat's tabular figures hold.** Measured live under
   `font-variant-numeric: tabular-nums`: a run of 1s and a run of 8s render at identical
   width (78.41px for seven digits). No numeric-mono fallback was needed; money, refs,
   and dates use `tabular-nums` on Montserrat throughout.
3. **Task 0's wrong figure also lived in two more places.** Beyond the report, the B2a
   changelog note said "Five of seven live files moved" (corrected in the addendum commit
   `c5de71b`) and the roadmap's Phase-B entry said the same (corrected in this commit's
   roadmap rewrite). The report + ledger corrections are commit `ce5cc61`.
4. **The design export exists** at `docs/design/Deals directions.dc.html` (slightly
   different filename than the brief's guess) and served as the visual reference; the
   spec's amendments (fonts, lime law) won where they differed.
5. **The brief's five next-action wirings do not cover every reachable step**, so the
   one mapping carries four more honest manual entries (deviation, stated): `qualify` →
   "Reach out and qualify", `plan` → "Present the options", `with_lender` → "Nudge the
   lender" (all manual, no route, notes from the steps' own SOP lines), and
   `broker_complete`/`compliance_package` → "Assemble compliance package" (manual, routed
   to the room's Complete & paid section) — without these, Broker Complete and
   with-lender files would have carried decorative blanks. The five briefed wirings are
   implemented exactly as specified.

### Task 6 — The compliance step (Complete & paid)

- The phase's steps are now **Broker complete → Compliance package → Paid**
  (config/lifecycle.ts). Stage places the file in the phase; the compliance status and
  the recorded commission move the steps within it (`closeoutStepStates`, pure, tested):
  a Broker Complete file with no package reads broker-complete as the now-work; a
  submitted package moves it done; a rejected package loops the compliance step back to
  current, amber, honestly; a funded file with no package reads the package as owed.
- **The read-only card** ([CloseoutPanel.tsx](../components/admin/deals/CloseoutPanel.tsx)):
  not started states the by-hand path (assemble per the BRX Ontario checklist, submit
  with the compliance submission skill); under review shows the raw Zoho value; approved
  is green; rejected is amber with "Fix it and submit it again"; unread says so. **Paid**
  reads the commission truth the Revenue surface uses (`Total_Commission` > 0 is the
  actual; 0 means not recorded, never a free deal) — recorded shows the figure, else the
  quiet "not recorded yet". The workbench **package checker is a named capability
  placeholder** (gray, dashed: what it will be, what it waits on) — no faked checklist
  state.
- **The one field addition**: `getDealCloseout` in [lib/zoho-admin.ts](../lib/zoho-admin.ts)
  reads `Deal_Name` (the band's client name), `Compliance_Status` (the new field), and
  `Total_Commission` (the commission truth the brief names) for the room's linked deal.
  Read-only, demo-guarded to fixtures, resilient (a 400 on the field retries without it
  and the card reads "not read"). Ask Fox's own deal fetch is untouched.

### Task 8 — The version toast

[lib/sw-update.ts](../lib/sw-update.ts) is the pure detection (unit-tested): a waiting
worker in state `installed` behind an existing controller, an `updatefound` →
`statechange` landing on `installed` with a controller, or `controllerchange` on a page
that HAD a controller at load (a first install claiming clients is not an update).
[ServiceWorkerRegister.tsx](../components/ServiceWorkerRegister.tsx) wires those events
and shows the quiet toast — "A new version is ready." with a Refresh button and a
dismiss. **Never auto-reloads.** Manual proof for the next deploy: open the installed
PWA (or a tab that has the current SW), deploy, reload once so the browser fetches the
new sw.js, and the toast should appear when the new worker finishes installing; press
Refresh and confirm the new BUILD_TIME on Status.
